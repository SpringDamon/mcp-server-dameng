# 每周工程回顾

生成一份全面的工程回顾报告，分析提交历史、工作模式和代码质量指标。具备团队感知能力：识别运行命令的用户，然后分析每位贡献者，提供个人表扬和成长机会。

## 参数

- 默认值：最近 7 天
- `24h`：最近 24 小时
- `14d`：最近 14 天
- `30d`：最近 30 天
- `compare`：对比当前时间窗口与上一个相同长度的窗口

## 使用说明

解析参数以确定时间窗口。默认为 7 天。所有时间都应使用用户的**本地时区**报告。

**午夜对齐窗口：** 对于以天为单位的时间窗口，计算本地午夜时间作为绝对起始日期。例如，如果今天是 2026-03-18 且窗口为 7 天，则起始日期为 2026-03-11。在 git log 查询中使用 `--since="2026-03-11T00:00:00"`。对于以小时为单位的时间窗口，使用 `--since="N hours ago"`。

---

### 步骤 1：收集原始数据

首先，拉取远程仓库并识别当前用户：

```bash
git fetch origin main --quiet
git config user.name
git config user.email
```

`git config user.name` 返回的名字就是**"你"**……即阅读本次回顾报告的人。所有其他作者都是你的团队成员。

执行以下所有 git 命令（它们相互独立）：

```bash
# 所有提交记录，包含时间戳、主题、哈希值、作者、变更文件数
git log origin/main --since="<window>" --format="%H|%aN|%ae|%ai|%s" --shortstat

# 每次提交的测试代码与总代码行数的细分，包含作者信息
git log origin/main --since="<window>" --format="COMMIT:%H|%aN" --numstat

# 提交时间戳，用于会话检测和小时分布分析
git log origin/main --since="<window>" --format="%at|%aN|%ai|%s" | sort -n

# 变更最频繁的文件（热点分析）
git log origin/main --since="<window>" --format="" --name-only | grep -v '^$' | sort | uniq -c | sort -rn

# 从提交消息中提取 PR 编号
git log origin/main --since="<window>" --format="%s" | grep -oE '[#!][0-9]+' | sort -t'#' -k1 | uniq

# 每位作者的文件热点
git log origin/main --since="<window>" --format="AUTHOR:%aN" --name-only

# 每位作者的提交数量
git shortlog origin/main --since="<window>" -sn --no-merges

# 测试文件总数
find . -name '*.test.*' -o -name '*.spec.*' -o -name '*_test.*' -o -name '*_spec.*' 2>/dev/null | grep -v node_modules | wc -l

# 时间窗口内变更的测试文件数
git log origin/main --since="<window>" --format="" --name-only | grep -E '\.(test|spec)\.' | sort -u | wc -l
```

### 步骤 2：计算指标

计算并以摘要形式展示以下指标：

- **推送到 main 分支的提交数：** N
- **贡献者数量：** N
- **合并的 PR 数：** N
- **总新增行数：** N
- **总删除行数：** N
- **净增代码行数（LOC）：** N
- **测试代码行数（新增）：** N
- **测试代码占比：** N%
- **版本范围：** vX.Y.Z → vX.Y.Z
- **活跃天数：** N
- **检测到的工作会话数：** N
- **平均每小时/会话代码行数：** N

然后在下方立即展示**每位作者的排行榜**：

```
贡献者               提交数   +/-           主要领域
你 (garry)              32   +2400/-300   browse/
alice                    12   +800/-150    app/services/
bob                       3   +120/-40     tests/
```

按提交数降序排列。当前用户始终显示在最前面，标注为"你（名字）"。

---

### 步骤 3：提交时间分布

以本地时间显示小时分布直方图：

```
小时  提交数  ████████████████
 00:    4      ████
 07:    5      █████
 ...
```

识别以下内容：
- 高峰时段
- 低谷时段
- 双峰模式（早/晚）还是连续模式
- 深夜编码集群（晚上 10 点之后）

---

### 步骤 4：工作会话检测

使用**45 分钟间隔**阈值来检测连续提交之间的会话。

会话分类：
- **深度会话**（50 分钟以上）
- **中等会话**（20-50 分钟）
- **微会话**（少于 20 分钟，仅单次提交）

计算：
- 总有效编码时间
- 平均会话时长
- 每小时有效时间的代码行数

---

### 步骤 5：提交类型分布

按照约定的提交前缀进行分类（feat/fix/refactor/test/chore/docs）。以百分比条形图展示：

```
feat:     20  (40%)  ████████████████████
fix:      27  (54%)  ███████████████████████████
refactor:  2  ( 4%)  ██
```

如果修复（fix）比例超过 50% 则发出警告……这表明一种"快速交付、快速修复"的模式，可能意味着代码审查存在不足。

---

### 步骤 6：热点分析

展示变更次数最多的前 10 个文件。标注：
- 变更 5 次及以上的文件（高 churn 热点）
- 热点列表中测试文件与生产文件的对比
- VERSION/CHANGELOG 文件的变更频率

---

### 步骤 7：PR 规模分布

估算 PR 的代码规模并进行分类：
- **小型**（少于 100 行代码）
- **中型**（100-500 行代码）
- **大型**（500-1500 行代码）
- **超大型**（1500 行以上代码）

---

### 步骤 8：专注度评分 + 本周最佳交付

**专注度评分：** 涉及变更最多的顶级目录的提交所占的百分比。越高 = 工作越专注深入。越低 = 上下文切换越频繁分散。

**本周最佳交付：** 时间窗口内代码行数变更最多的单个 PR。突出显示 PR 编号、变更行数以及其重要性。

---

### 步骤 9：团队成员分析

对每位贡献者（包括当前用户），计算以下内容：

1. **提交数与代码行数**……总提交数、新增、删除、净增代码行数
2. **专注领域**……他们最常修改的目录/文件（前 3 个）
3. **提交类型分布**……个人的 feat/fix/refactor/test 比例
4. **会话模式**……他们的编码时间（高峰时段）、会话数量
5. **测试纪律**……个人的测试代码占比
6. **最大交付**……影响力最大的单次提交或 PR

**对于当前用户（"你"）：** 提供最深入的分析。包含所有会话分析、时间模式、专注度评分。使用第一人称叙述。

**对于每位团队成员：** 用 2-3 句话描述他们交付的内容和工作模式。然后：

- **表扬**（1-2 项具体内容）：基于实际提交记录。不要只说"做得好"……要具体说明哪里做得好。
- **成长机会**（1 项具体内容）：以能力提升为框架，而非批评。基于实际数据。

**如果是单人仓库：** 跳过团队分析部分。

**AI 协作：** 如果提交记录中包含 `Co-Authored-By` AI 署名信息，将"AI 辅助提交"作为单独的指标进行追踪。

---

### 步骤 10：周环比趋势（当窗口 >= 14 天时）

按周进行分组并展示趋势：
- 每周提交数（总计和按作者）
- 每周代码行数
- 每周测试比例
- 每周修复比例
- 每周会话数量

---

### 步骤 11：连续提交追踪

从今天往前推算，统计至少有 1 次提交的连续天数：

```bash
# 团队连续提交天数
git log origin/main --format="%ad" --date=format:"%Y-%m-%d" | sort -u

# 个人连续提交天数
git log origin/main --author="<user_name>" --format="%ad" --date=format:"%Y-%m-%d" | sort -u
```

展示两者：
- "团队交付连续天数：47 天"
- "你的交付连续天数：32 天"

---

### 步骤 12：加载历史与对比

检查 `memory/` 中是否存在历史回顾记录：

如果存在历史回顾记录，加载最近的一次并计算变化量：

```
                    上次        现在        变化
测试比例：         22%    →    41%         ↑19个百分点
会话数：           10     →    14          ↑4
每小时代码行数：   200    →    350         ↑75%
修复比例：         54%    →    30%         ↓24个百分点（改善中）
```

如果不存在历史回顾记录，注明"首次记录回顾，请在下周再次运行以查看趋势。"

---

### 步骤 13：保存回顾历史

将 JSON 快照保存到 `memory/retro-YYYY-MM-DD.json`，包含指标、作者、版本范围、连续天数和可分享的摘要。

---

### 步骤 14：撰写叙述报告

**Telegram 格式**（使用项目符号、加粗，最终输出中不使用 Markdown 表格）。

结构：

**一句话摘要**（第一行）：
> 3月1日当周：47 次提交（3 位贡献者），3.2k 行代码，38% 测试，12 个 PR，高峰：晚上 10 点 | 连续提交：47 天

然后依次展示以下章节：

- **摘要**……核心指标
- **与上次回顾的趋势对比**……变化量（首次回顾时跳过）
- **时间与会话模式**……团队编码时间分布、会话时长、深度会话与微会话对比
- **交付速度**……提交类型、PR 规模、修复链检测
- **代码质量信号**……测试比例、热点、代码 churn
- **专注度与亮点**……专注度评分、本周最佳交付
- **你的一周**……当前用户的个人深度分析
- **团队分析**……每位团队成员的分析，包含表扬与成长建议（单人仓库跳过）
- **团队前 3 项成就**……影响力最大的交付内容
- **3 项待改进之处**……具体、可执行、基于提交记录
- **下周 3 个习惯**……小而实用、易于执行（采用时间少于 5 分钟）

---

## 对比模式

当用户说"compare"（对比）时：
- 为当前时间窗口运行回顾
- 为上一个相同长度的时间窗口运行回顾
- 并排展示指标，用箭头标注改善或退步
- 简要叙述最大的变化

---

## 重要规则

- **所有时间使用本地时区。** 切勿设置 `TZ` 环境变量。
- **使用 Telegram 格式。** 使用项目符号和加粗。最终输出中避免使用 Markdown 表格。
- **表扬基于提交记录。** 不要只说"做得好"，必须明确指出哪里做得好。
- **成长建议基于数据。** 没有证据支持时不要提出批评。
- **保存历史记录。** 每次回顾都保存到 `memory/` 目录中用于趋势追踪。
- **完成状态：**
  - DONE……回顾已生成，历史记录已保存
  - DONE_WITH_CONCERNS……已生成但缺少部分数据（例如没有历史回顾可供对比）
  - BLOCKED……不在 git 仓库中或时间窗口内没有提交

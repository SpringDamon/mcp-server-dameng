# 系统化调试

## 铁律

**在未进行根因调查之前，不得进行任何修复。**

盲目修复症状只会导致"打地鼠式"的调试。每次未能解决根因的修复都会让下一个bug更难被发现。找到根因，然后再修复。

---

## 第一阶段：根因调查

在形成任何假设之前，先收集上下文信息。

1. **收集症状：** 阅读错误消息、堆栈跟踪和复现步骤。如果用户没有提供足够的上下文，每次只问一个问题。不要一次性问五个问题。

2. **阅读代码：** 从症状出发，沿着代码路径回溯到潜在原因。搜索所有相关引用，阅读故障点周围的逻辑。

3. **检查近期变更：**
   ```bash
   git log --oneline -20 -- <affected-files>
   ```
   这个功能之前能正常工作吗？发生了什么变化？如果是回归问题，说明根因就在差异中。

4. **复现：** 你能确定性地触发这个bug吗？如果不能，在继续之前收集更多证据。

5. **检查记忆** 中是否有针对同一区域的先前调试会话。同一文件中反复出现的bug是架构设计不当的信号（architectural smell）。

输出：**"根因假设：..."** ... 一个关于什么地方出错以及为什么出错的、具体且可验证的论断。

---

## 第二阶段：模式分析

检查这个bug是否符合已知模式：

**竞态条件（Race condition）** ... 间歇性出现，依赖时序。检查对共享状态的并发访问。

**空值传播（Nil/null propagation）** ... NoMethodError、TypeError。缺少对可选值的保护检查。

**状态损坏（State corruption）** ... 数据不一致、部分更新。检查事务、回调、钩子函数。

**集成失败（Integration failure）** ... 超时、意外响应。外部API调用、服务边界。

**配置漂移（Configuration drift）** ... 本地能运行，在预发/生产环境失败。环境变量、功能开关、数据库状态。

**缓存过期（Stale cache）** ... 显示旧数据，清除缓存后修复。Redis、CDN、浏览器缓存。

同时检查：
- 项目已知问题中是否有相关问题
- Git日志中同一区域的先前修复。同一文件中反复出现的bug是架构设计问题，不是巧合。

**外部搜索：** 如果bug不符合已知模式，在网上搜索错误类型。**先脱敏：** 去除主机名、IP地址、文件路径、SQL语句、客户数据。搜索错误类别，而不是原始消息。

---

## 第三阶段：假设验证

在编写任何修复代码之前，先验证你的假设。

1. **确认假设：** 在疑似根因处添加临时日志语句、断言或调试输出。运行复现步骤。证据是否匹配？

2. **如果假设错误：** 搜索错误（先脱敏敏感数据）。回到第一阶段。收集更多证据。不要猜测。

3. **三次失败规则：** 如果3个假设都失败了，**停止**。告诉用户：

   "已测试3个假设，均不匹配。这可能是架构问题，而非简单bug。"

   选项：
   - 用新假设继续调查（描述它）
   - 升级给人工审查（需要了解系统的人）
   - 添加日志并等待（对该区域进行监控，下次捕获它）

**危险信号** ... 如果你看到以下情况，请放慢速度：
- "先来个临时修复" ... 没有"临时"这回事。要么正确修复，要么升级处理。
- 在追踪数据流之前就提出修复方案 ... 你是在猜测。
- 每次修复都在其他地方暴露出新问题 ... 选错了抽象层，而不是代码错误。

---

## 第四阶段：实现

一旦确认根因：

1. **修复根因，而非症状。** 用最小的改动消除实际问题。

2. **最小化差异：** 涉及最少的文件，改动最少的代码行。抵制重构相邻代码的冲动。

3. **编写回归测试**，要求：
   - **在修复前失败**（证明测试是有意义的）
   - **在修复后通过**（证明修复有效）

4. **运行完整测试套件。** 不允许出现回归。

5. **如果修复涉及超过5个文件：** 在继续之前向用户标注影响范围（blast radius）。对于bug修复来说，这太大了。

---

## 第五阶段：验证与报告

**重新验证：** 复现原始bug场景并确认已修复。这一步不可省略。

运行测试套件。

输出结构化的调试报告：

**DEBUG REPORT**
- **Symptom（症状）：** 用户观察到的现象
- **Root cause（根因）：** 实际上哪里出了问题
- **Fix（修复）：** 改了什么，附带文件引用
- **Evidence（证据）：** 测试输出、复现结果证明修复有效
- **Regression test（回归测试）：** 新测试的位置
- **Related（相关）：** 同一区域的先前bug、架构备注
- **Status（状态）：** DONE | DONE_WITH_CONCERNS | BLOCKED

将报告保存到 `memory/` 目录，以今天的日期命名，以便未来会话参考。

---

## 重要规则

- **3次以上修复尝试失败：停止并质疑架构设计。** 是架构问题，不是假设失败。
- **永远不要应用你无法验证的修复。** 如果你不能复现并确认，就不要提交。
- **永远不要说"这应该能修好"。** 验证并证明它。运行测试。
- **如果修复涉及超过5个文件：** 在继续之前向用户标注。
- **完成状态：**
  - DONE ... 找到根因，应用修复，编写回归测试，所有测试通过
  - DONE_WITH_CONCERNS ... 已修复但无法完全验证（例如间歇性bug，需要特定环境）
  - BLOCKED ... 调查后根因仍不清楚，已升级处理
